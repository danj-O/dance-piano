# Phase 5 Results — Generic trigger modules

## Scope and runtime flow

The built-in layout remains the familiar sixteen-key piano. A development-only mixed layout proves that a keyboard and two freely placed triggers can coexist. The path is:

```text
layout → keyboard/trigger modules → generated zones
camera frame + shared baseline + zone geometry → activity ratios
ZoneTracker → trigger/release events → action dispatcher
note or drum action → DanceAudio → existing effects, mute, and output
```

Neither the detector nor either calibration controller reads an action type, sound, or module type. Layouts remain version-1 in-memory objects; no editor or saved layout format was added. The four existing localStorage keys and their record shapes are unchanged.

## Trigger model and validation

The module is user-facing configuration. It generates a separate runtime zone:

```js
{
  id: 'trigger-left', type: 'trigger',
  transform: { x: 0.78, y: 0.38, width: 0.14, height: 0.20 },
  label: 'KICK',
  action: { type: 'drum', sound: 'kick' }
}

// Generated by generateZones(layout):
{
  id: 'trigger-left:zone-0', moduleId: 'trigger-left',
  geometry: { x: 0.78, y: 0.38, width: 0.14, height: 0.20 },
  label: 'KICK', action: { type: 'drum', sound: 'kick' }
}
```

One trigger currently generates one zone, but the two objects have separate identities and copies of geometry/action data. IDs and output order are deterministic. The trigger can also carry a supported note action, so it is not inherently percussion. Module IDs must be unique nonempty strings. Geometry must be finite, positive in size, and wholly inside normalized camera bounds; invalid and overlapping rectangles throw before zone generation. Rotation and per-module sensitivity overrides are not part of Phase 5. Triggers inherit the current global detection settings.

## Development layout and mirrored coordinates

Use `python3 -m http.server 8000`, then visit `http://localhost:8000/index.html?layout=percussion-demo`. This query selects `createMixedDemoLayout` for the page session only. Removing it reloads the classic keyboard. The demo contains the original keyboard module plus `trigger-left` (kick) and `trigger-right` (snare), above the strip with no overlap.

Zone geometry is in unmirrored camera coordinates. `displayRect` converts it for the mirrored canvas: screen x = camera-view x + `(1 - zone.x - zone.width) × view width`. Thus the camera-right trigger at x = 0.78 appears on the performer's left; the camera-left trigger at x = 0.08 appears on the right. Detection uses the original geometry, and dispatch follows the same zone ID, so left/right sounds are not swapped. Tests assert the screen rectangles and preserve the keyboard's low-to-high mirrored note order.

The canvas draws trigger zones as cyan outlined blue regions labeled KICK/SNARE. Occupancy is yellow and a played trigger flashes green, matching the key feedback. The optional percentage readout and existing local drift/recovery bars include triggers. Settings outlines every module; the detector telemetry uses trigger labels alongside numbered keyboard rows.

## Actions and audio

`dispatchZoneEvent` handles `note` and `drum` explicitly. A drum `trigger` calls `DanceAudio.playDrum(sound)` once; its `release` remains in the event pipeline but does nothing musically. Note one-shot and gate behavior is unchanged. The tracker still owns occupancy, two-frame rearm, and cooldown, so holding a pad cannot replay it and leaving/re-entering can fire it again.

Kick is a short sine oscillator with a falling pitch and amplitude. Snare combines a short filtered noise buffer with a triangle oscillator. Both use the existing audio input, so the current reverb, delay, compressor, and master mute apply. Percussion voices own their source nodes, disconnect after all sources end, and stop on camera shutdown or all-notes-off. Simultaneous and repeated drum hits do not share voice ownership with notes or one another. No samples or asset loading were added.

## Mixed detection and calibration

Before this phase, broad-change suppression triggered when at least half of **all** supplied zones were above the press threshold. Eight active classic keys therefore suppressed a broad event in the sixteen-key layout. Adding two trigger zones would raise that count to nine, letting the same eight-key broad change through. Large trigger geometry did not directly distort the count because the policy counted zones rather than area; their addition changed its denominator.

The smallest generic fix keeps the half-of-zones test for the whole layout and adds the same test within any module group containing at least four zones. At least four zones must be active before broad suppression can engage. The classic keyboard therefore still suppresses at eight active keys with or without the two triggers. One or both single-zone triggers can play together, while an obvious change across many zones still suppresses entries. The rule depends only on zone IDs and module grouping, never on keyboard/drum types. The detector continues to disarm a suppressed entry until release, as before. Tests cover the classic and mixed eight-key boundary, seven-key interaction, two simultaneous pads, and all-zone changes.

The two triggers use the same measurement, shared baseline, `ZoneTracker`, local adaptation, and global idle controller as keys. A stable low reading in a trigger can adapt locally; a high or active reading freezes it. The mixed layout has eighteen zones, so global idle calibration requires nine safe low zones and considers the trigger zones in both eligibility and refresh. A high trigger blocks global refresh as a safety rule, then a fresh manual/camera reference resets all temporal state. The shared baseline writes nonoverlapping trigger/key pixels once each. A large camera move or a stationary object can still resemble occupancy or drift; the manual empty-view fallback remains available.

## Verification and limits

The complete Node suite passes **88 tests**, including deterministic coverage of module validation, stable generated IDs, arbitrary trigger rectangles, mirrored mapping, mixed frame measurement, independent and simultaneous note/drum events, hold/release/re-entry, finite kick/snare cleanup, classic and mixed broad suppression, local adaptation, high occupancy and subsequent clearance, global idle refresh, and manual/camera reset behavior. `node --check src/app.js` and `git diff --check` also pass.

The localhost browser loaded the demo query, opened Settings and Instrument, and reported no console errors. Starting the camera remained at the browser's permission/wait state in this environment, so live overlay alignment, physical triggering, actual speaker timbre, and the following interaction checks are **not claimed as verified** here.

For manual acceptance, open the demo URL on a camera-capable device, clear all three regions for reference capture, then verify: each pad sounds on entry and not on exit or hold; re-entry sounds again; keyboard notes and both pads can sound together; KICK appears on the performer's left and SNARE on the right; percentages/debug rows and local bars cover all eighteen zones; manual calibration resets them. Check desktop and mobile. Clear the regions and let normal low drift recover; a large camera move should prompt manual recalibration rather than learn occupied regions.

Known limits: overlapping modules are rejected because their shared baseline pixels would otherwise receive ambiguous updates; large trigger areas can dilute a small hand/object's changed-pixel ratio, so geometry and global Step sensitivity still need physical tuning; a low stationary object below the adaptation ceiling can resemble environmental drift; the global controller still requires at least two safe low zones; the broad guard is conservative for layouts with many active zones. There is no module inspector, drag/resize, trigger-specific setting, layout persistence, or saved layout manager.

Phase 6 should prevent invalid/overlapping placements in the editor, preserve camera-coordinate geometry during touch manipulation, bind inspector fields to module configuration rather than global Settings, and validate any future saved layout before replacing the recoverable classic default. None of that is implemented in Phase 5.
